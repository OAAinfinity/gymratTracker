# GymRatTracker Technical Reference

Last updated: 2026-04-17

## Purpose

This document is the single source of truth for:

1. API endpoint contracts
2. Firestore schema contracts
3. State transitions by page/feature
4. Migration plan to remove legacy inches path with minimal risk

## System Overview

GymRatTracker is a monorepo with:

1. Frontend web app (React + Vite)
2. Backend API (Express) for health checks and Razorpay payment operations
3. Firestore + Firebase Auth for core application data and identity
4. Optional Firebase Functions runtime for backend pathing under Hosting rewrites

Core directories:

1. frontend: UI, auth handling, Firestore reads/writes, payment orchestration
2. backend: Express API for payment order creation and verification
3. functions: Express app for Firebase Functions deployment mode
4. shared: reserved for future shared contracts/types

## 1. API Endpoint Contracts

### 1.1 Backend Service Base

When deployed as standalone backend (Render/Vercel/Node host):

1. Base URL comes from frontend env VITE_API_BASE_URL
2. Frontend has fallback selection logic among configured and hardcoded candidates

### 1.2 Health Endpoint

Method: GET
Path: /api/health
Auth required: No
Request body: None
Response 200:

```json
{
  "status": "ok",
  "readiness": "ready",
  "service": "fitness-tracker-backend",
  "timestamp": "2026-04-17T00:00:00.000Z"
}
```

Errors:

1. 404 route not found if host/router mismatch
2. 500 internal server error for unhandled server errors

### 1.3 Create Payment Order

Method: POST
Path: /api/payments/create-order
Auth required by backend: No (frontend requires signed-in user before invoking)
Request body:

```json
{
  "plan": "monthly"
}
```

Allowed plan values:

1. monthly
2. yearly

Server-side plan config:

1. monthly: amount 6900 INR paise, 30 days
2. yearly: amount 39900 INR paise, 365 days

Success 200:

```json
{
  "status": "ok",
  "keyId": "rzp_live_or_test_key",
  "order": {
    "id": "order_xxx",
    "entity": "order",
    "amount": 6900,
    "currency": "INR"
  },
  "plan": "monthly",
  "days": 30
}
```

Client expectations:

1. status must be ok
2. keyId must be present
3. order.id must be present

Error responses:

1. 400 invalid subscription plan
2. 500 Razorpay keys missing or order creation failure

### 1.4 Verify Payment

Method: POST
Path: /api/payments/verify
Auth required by backend: No (verification based on signature)
Request body:

```json
{
  "razorpay_order_id": "order_xxx",
  "razorpay_payment_id": "pay_xxx",
  "razorpay_signature": "hex_hmac",
  "plan": "monthly"
}
```

Verification logic:

1. HMAC SHA256 over orderId|paymentId
2. Compare with provided signature

Success 200:

```json
{
  "status": "ok",
  "verified": true,
  "subscription": {
    "subscriptionPlan": "monthly",
    "subscriptionEndDate": "2026-05-17",
    "subscriptionExpiresAt": "2026-05-17T12:00:00.000Z"
  }
}
```

Error responses:

1. 400 missing data or invalid signature
2. 500 missing Razorpay secret

### 1.5 Backend Non-Route Behaviors

CORS:

1. CORS_ORIGIN env supports comma-separated allowlist
2. credentials enabled
3. origin not allowed returns 403 with explicit message

Global error/404:

1. unknown route returns 404 JSON
2. unhandled exceptions return 500 JSON

## 2. Firestore Schema Contract

## 2.1 Auth Principal

All ownership checks use request.auth.uid.

## 2.2 Collection: users

Document ID: uid

Required fields by current rules validation:

1. name string
2. email string
3. goal string
4. weightUnit string
5. measureUnit string
6. accent string
7. goalWeight string
8. age string
9. height string

Optional subscription fields with constraints:

1. subscriptionPlan in [none, monthly, yearly]
2. subscriptionEndDate string or absent
3. subscriptionExpiresAt timestamp, null, or absent

Observed additional fields written by app (currently allowed because rules do not forbid extra fields):

1. createdAt timestamp
2. subscriptionStatus string
3. subscriptionActivatedAt timestamp
4. subscriptionPaymentId string
5. subscriptionOrderId string

Permissions:

1. read owner only
2. create/update owner only + validUserDoc shape
3. delete owner only

## 2.3 Subcollection: users/{uid}/measurements

Document ID: dateKey formatted YYYY-MM-DD

Required fields:

1. date timestamp
2. dateKey string
3. waist number
4. chest number
5. hips number
6. thigh number
7. arms number

Optional fields:

1. notes string

Observed additional fields written by app:

1. updatedAt timestamp

Permissions:

1. read owner only
2. create/update owner only + validUserDailyMeasurementDoc
3. delete owner only

## 2.4 Collection: weights

Document ID: generated by addDoc

Required fields:

1. uid string
2. weight number
3. date string

Optional fields:

1. note string

Observed additional fields:

1. createdAt timestamp

Permissions:

1. read if resource uid equals auth uid
2. create/update if request uid equals auth uid and validWeightDoc
3. delete if resource uid equals auth uid

## 2.5 Collection: measurements (legacy)

Document ID: generated by addDoc

Required fields:

1. uid string
2. part string
3. val number
4. date string

Observed additional fields:

1. createdAt timestamp

Permissions:

1. read if resource uid equals auth uid
2. create/update if request uid equals auth uid and validMeasurementDoc
3. delete if resource uid equals auth uid

## 2.6 Collection: workouts

Document ID: generated by addDoc

Required fields:

1. uid string
2. exercise string
3. sets number
4. reps number
5. weight number
6. muscle string
7. rpe number
8. date string

Optional fields:

1. note string

Observed additional fields:

1. createdAt timestamp

Permissions:

1. read requires signed-in + active subscription + owner uid
2. create/update requires signed-in + active subscription + owner uid + validWorkoutDoc
3. delete requires signed-in + active subscription + owner uid

## 2.7 Composite Indexes

Defined composite indexes:

1. weights collectionGroup: uid ASC + date ASC
2. measurements collectionGroup: uid ASC + date ASC
3. workouts collectionGroup: uid ASC + date ASC

No custom index currently defined for users/{uid}/measurements subcollection query patterns.

## 3. State Transitions by Page

## 3.1 Global App Lifecycle

1. App renders AuthProvider.
2. AuthProvider initializes Firebase app/auth/db once.
3. onAuthStateChanged drives user state:
   - undefined: loading
   - null: unauthenticated
   - user object: authenticated
4. AppShell reads users/{uid} profile and merges into settings state.
5. Selected page component receives settings and optional setSettings.

## 3.2 Auth Page

States:

1. mode in [login, register, reset]
2. busy boolean
3. err message
4. msg success info

Transitions:

1. login success -> auth state becomes user -> AppShell mounts
2. register success -> creates users/{uid} default profile -> auth state user
3. google success:
   - if first login: creates users/{uid}
   - else no profile creation
4. reset success -> informational msg shown

Failure transitions:

1. firebase auth codes mapped to readable message
2. busy always reset in finally

## 3.3 Dashboard

Reads:

1. weights top-level collection by uid
2. measurements legacy top-level collection by uid
3. workouts top-level collection by uid

Derived state:

1. current/start weight and deltas
2. latest and first measurements by PARTS list
3. weekly workouts summary
4. recent activity merged timeline

Key caveat:

1. dashboard uses legacy top-level measurements data, not new nested user daily measurements.

## 3.4 Weight Page

Form state:

1. weight
2. note
3. date
4. busy
5. err

Save transition:

1. validate weight non-empty
2. write weights addDoc with uid and createdAt
3. clear weight/note fields
4. onSnapshot auto-refreshes history

Delete transition:

1. deleteDoc by id
2. onSnapshot updates list

## 3.5 Inches Analytics Page (active)

Source of truth:

1. users/{uid}/measurements/{dateKey}

Form + save flow:

1. MeasurementForm emits payload with dateKey, notes, values (partial allowed)
2. Parent normalizes missing parts:
   - use provided numeric value if present
   - else fallback to latestEntry value
   - else 0
3. saveMeasurement setDoc at dateKey (upsert behavior)
4. onSnapshot updates entries and dependent chart/summary/history

Delete flow:

1. deleteDoc at users/{uid}/measurements/{dateKey}
2. onSnapshot updates UI

Derived analytics state:

1. range in [7, 30, all]
2. filteredEntries by latest date window
3. chart toggles by body part visibility
4. summary trends and plateau logic from current and all entries

## 3.6 Inches Page (legacy, not routed)

1. Uses top-level measurements documents by part/date
2. Still present in code but not selected in AppShell pages map
3. Technical debt and migration target

## 3.7 Gym Page

Precondition state:

1. subActive computed from settings subscription fields
2. if false -> paywall UI

Payment transition:

1. load Razorpay checkout script lazily
2. create-order API call with plan
3. open checkout
4. on handler callback -> verify API call
5. on verified response -> saveProfile users/{uid} with subscription fields
6. setSettings merge same values for immediate UI unlock

Workout logging transition (only when subActive true):

1. validate required exercise/sets/reps
2. add workout document via useAdd
3. clear form
4. grouped history and analytics recompute from onSnapshot data

Search/filter transition:

1. historyQuery filters by date text and localized weekday text
2. groups logs by normalized exercise key and then by date

## 3.8 Calculators Page

1. all state local to component
2. no persistence
3. deterministic derived values for BMR, TDEE, deficit, macro splits

## 3.9 Settings Page

State operations:

1. updates local settings object
2. saveAll writes merged settings to users/{uid}
3. signout calls Firebase signOut

Subscription display:

1. read-only reflection of settings subscription fields

## 4. Legacy Inches Migration Plan

Goal: remove top-level measurements dependency safely and make nested daily model the only inches source.

### Phase 0: Guardrails and snapshot

1. Backup Firestore before migration.
2. Freeze schema decisions (units, required body parts, date format).
3. Add monitoring for dashboard inch metrics parity.

### Phase 1: Read parity in UI

1. Update dashboard inch cards to read from users/{uid}/measurements.
2. Keep fallback read from legacy measurements only if nested data empty.
3. Release and verify no user-visible breakage.

Success criteria:

1. dashboard values match inches analytics page values for active users.

### Phase 2: Dual-write bridge (optional but safest)

1. During save in inches analytics, write nested document and legacy part rows.
2. Mark legacy rows with migration tag field for traceability.

Success criteria:

1. old dashboards and any external consumers still receive updates.

### Phase 3: One-time backfill

1. For each user legacy measurement row set, aggregate by date to produce waist/chest/hips/thigh/arms.
2. Write users/{uid}/measurements/{dateKey} documents for all historical dates.
3. Use batched writes and idempotent upserts.

Backfill rules:

1. dateKey from legacy date string
2. missing part values resolve by nearest previous date or 0 based on business decision
3. preserve notes if available else empty

### Phase 4: Switch all readers

1. Remove legacy measurements reads from Dashboard and any remaining views.
2. Confirm analytics, cards, and trends all consume nested data only.

Success criteria:

1. no frontend query for top-level measurements remains except migration tools.

### Phase 5: Stop legacy writes

1. Remove any dual-write bridge.
2. Keep legacy collection read-only for a deprecation window.

### Phase 6: Rules and index cleanup

1. Remove/disable top-level measurements write rules.
2. Add any needed indexes for nested query patterns if required.
3. Optionally keep legacy read access temporarily for rollback.

### Phase 7: Legacy data retirement

1. Export legacy collection snapshot for archive.
2. Delete top-level measurements documents in controlled batches.
3. Remove legacy code blocks including old InchesPage component.

Rollback strategy:

1. keep export snapshot
2. keep feature flag for legacy dashboard path until stable
3. revert reader switch if parity checks fail

## 6. Deployment Topologies

## 6.1 Firebase unified

1. Hosting serves frontend build
2. /api rewrites to Firebase Function api
3. Firestore rules/indexes deployed via firebase tools

Important note:

1. Current functions app exposes health route only.
2. Payment routes exist in backend service, not in functions app.
3. If you rely purely on Firebase Functions path, payment endpoints must be added there.

## 6.2 Vercel split

1. frontend project root frontend
2. backend project root backend
3. frontend calls backend via VITE_API_BASE_URL

## 6.3 Render split

1. backend web service
2. frontend static site
3. env linking done manually between services

## 7. Known Risks and Improvement Backlog

1. Data model split for inches causes inconsistent dashboard metrics.
2. Legacy InchesPage remains in source and increases maintenance risk.
3. Payment fallback uses hardcoded backend host in frontend; brittle in multi-env deployments.
4. Firestore rule validators allow extra untyped fields; stricter field allowlists could improve integrity.
5. Functions and backend route parity is incomplete.
6. App.jsx is monolithic; further component/service extraction will reduce regression risk.
